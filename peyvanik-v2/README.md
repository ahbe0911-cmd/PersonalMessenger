# Peyvanik v2 — Google + manual TOTP preview

Separate D1/KV from PersonalMessenger. Google ID token RS256 signature and strict issuer, audience, expiry, nonce, Gmail verification; account keyed by Google subject. Manual base32 setup key shown once, Authenticator SHA1 6 digits / 30 seconds, encrypted seed AES-GCM, one-use setup/login tickets, attempt limits, atomic replay counter, hashed 30-day session tokens, session revoke. Registration closed by default: requires actual GOOGLE_CLIENT_ID, TOTP_ENCRYPTION_KEY secret, REGISTRATION_OPEN=true only after security review and integration tests. Google login required on every new device in this initial flow; no email or QR. Device-to-device approval, optional password, recovery, UI/native clients and migration are not implemented yet. Google OAuth client must be created and browser origin configured; no embedded Google WebView login. Unit tests are not end-to-end authorization tests. Rate table and expired challenge cleanup needs scheduled maintenance before public launch. Existing personal app untouched. No E2EE; 20 MiB/file, 50 MiB/account, 300 MiB/project initial quotas. No public registration yet.

## Phase 3 security preview
Optional additional password (min 12 chars, PBKDF2 SHA-256 100k iterations plus server pepper), requires fresh Authenticator for change/disable, existing password if set. After verified Google identity, existing sessions can display or deny a dedicated 5-minute device code instead of TOTP; optional password still required. Eight 128-bit single-use recovery codes, hashed, generated only with fresh Authenticator and existing password; recovery replaces TOTP for a login, not Google or extra password. Session list, individual revoke and revoke-all-other endpoints, last-seen throttled to 5 min. Password change revokes other sessions and outstanding challenges. Codes never appear in chat. No push delivery or UI yet; active client will poll security requests. Registration remains closed. No production deployment in this phase; OAuth config, migration application, cleanup and end-to-end review still needed.

## Phase 4 direct chat preview
Exact case-insensitive username lookup (no public email), profile update, unique direct conversation, text send with client UUID idempotency, history pagination, per-chat event sync, two-party deletion tombstones and block/unblock. All routes require authenticated account; unrelated accounts cannot read, send or delete. Block prevents discovery and new messages both ways but retains existing history. Initial limit 60 mutations/searches/min/account. Text only at this stage: chat attachments, voice, delivery/read receipts, groups, push and UI/native clients are still pending. Cloud items stay separate. Registration closed; no production deployment or database migration applied in this phase. Tests use local SQLite adapter, not live D1.

## Phase 5 My Cloud preview
Private notes and files, single-level folders, search, category filters, favorites, rename/move, cursor pagination, usage and quota enforcement, safe binary download, deletion and pending reservation inspection. Folder deletion moves items to root. Limits: 20 MiB/file, 50 MiB/account including note UTF-8 bytes, 300 MiB project, 2,000 items/account, 100 folders/account; 40 mutations/min. Incomplete uploads reserve space and can be removed after 24h; retry deleting state is allowed. No nested folders, file preview, editing note content, direct chat media, push or client UI yet. SQLite and in-memory KV tests, not live D1/KV. Migration not applied to production; public registration remains closed.

## Phase 6 responsive web client
RTL Persian adaptive UI with login/manual setup, chat/search/block, private cloud files/folders/notes/favorites, profile and security/session management. Browser uses same-origin proxy, Secure HttpOnly SameSite cookie, no token localStorage, strict path allowlist, origin/request-marker checks and CSP. Requires separate web Worker with API service binding and ASSETS binding pointing to web/; assets routed through Worker for security headers. Google client authorized web origin required. No real Google sign-in or live deployment verified, no embedded WebView Google login; native Android/Windows shells and builds remain for phase 7. System font fallback used; no bundled Vazirmatn yet. No E2EE, chat media, nested folders or native share integration. Tests include proxy assertions and static JS syntax, not actual browser end-to-end. Registration remains closed.

## Phase 7 preview packages
Android and Windows **browser launchers**, not complete native clients, separate app IDs/install paths. They open the public visual preview at https://peyvanik-preview.ahbe0911.workers.dev/ using the system browser. Preview worker is deliberately disconnected from any account DB; registration and messaging are disabled. Build workflow outputs debug APK and unsigned x64 setup. Windows launcher docks right at 35% width; the external browser controls its own window. Native share, embedded authenticated session, notifications and release signing remain pending. Full deployment requires actual Google OAuth client ID, server key, migrations and real integration/security tests. Existing PersonalMessenger remains unchanged.

## Operational staging
Actual web Worker `peyvanik-web` uses private `peyvanik-v2-api` service binding and bundled assets. Preview remains separate. Database migrations 002–005 and API deployment performed independently. Registration remains gated until Google web client ID is configured and real sign-in verified. Encryption secret configured server-side, never in source. Desktop/mobile launcher remains a browser-based preview package; native client work remains pending. No migration of PersonalMessenger data.

## Key access mode
Separate high-entropy 256-bit account keys, generated server-side, hash only stored, one-time display. No Google, email or TOTP required for key accounts. Initial 100-account pilot cap, fixed-window abuse limits, existing session revocation. No self-service lost-key recovery; keep key safe. Google routes remain gated off. KEY_AUTH_OPEN controls registration/login. Never reuse legacy shared enrollment key.

## Keymaker
Dedicated web /keymaker and Windows native key issuer. Public signup policy unchanged; creates new accounts only, never resets existing keys, no admin access, no session issued, same limits. Server response only displays new key once. Explicit text export stores plaintext; handle carefully. Network required. Windows executable unsigned.
