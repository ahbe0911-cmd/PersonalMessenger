# Peyvanik v2 — Google + manual TOTP preview

Separate D1/KV from PersonalMessenger. Google ID token RS256 signature and strict issuer, audience, expiry, nonce, Gmail verification; account keyed by Google subject. Manual base32 setup key shown once, Authenticator SHA1 6 digits / 30 seconds, encrypted seed AES-GCM, one-use setup/login tickets, attempt limits, atomic replay counter, hashed 30-day session tokens, session revoke. Registration closed by default: requires actual GOOGLE_CLIENT_ID, TOTP_ENCRYPTION_KEY secret, REGISTRATION_OPEN=true only after security review and integration tests. Google login required on every new device in this initial flow; no email or QR. Device-to-device approval, optional password, recovery, UI/native clients and migration are not implemented yet. Google OAuth client must be created and browser origin configured; no embedded Google WebView login. Unit tests are not end-to-end authorization tests. Rate table and expired challenge cleanup needs scheduled maintenance before public launch. Existing personal app untouched. No E2EE; 20 MiB/file, 50 MiB/account, 300 MiB/project initial quotas. No public registration yet.

## Phase 3 security preview
Optional additional password (min 12 chars, PBKDF2 SHA-256 100k iterations plus server pepper), requires fresh Authenticator for change/disable, existing password if set. After verified Google identity, existing sessions can display or deny a dedicated 5-minute device code instead of TOTP; optional password still required. Eight 128-bit single-use recovery codes, hashed, generated only with fresh Authenticator and existing password; recovery replaces TOTP for a login, not Google or extra password. Session list, individual revoke and revoke-all-other endpoints, last-seen throttled to 5 min. Password change revokes other sessions and outstanding challenges. Codes never appear in chat. No push delivery or UI yet; active client will poll security requests. Registration remains closed. No production deployment in this phase; OAuth config, migration application, cleanup and end-to-end review still needed.

## Phase 4 direct chat preview
Exact case-insensitive username lookup (no public email), profile update, unique direct conversation, text send with client UUID idempotency, history pagination, per-chat event sync, two-party deletion tombstones and block/unblock. All routes require authenticated account; unrelated accounts cannot read, send or delete. Block prevents discovery and new messages both ways but retains existing history. Initial limit 60 mutations/searches/min/account. Text only at this stage: chat attachments, voice, delivery/read receipts, groups, push and UI/native clients are still pending. Cloud items stay separate. Registration closed; no production deployment or database migration applied in this phase. Tests use local SQLite adapter, not live D1.
